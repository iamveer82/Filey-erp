# Filey AI quick replies

Filey AI previously forced provider reasoning on for every managed request. It now defaults to quick replies with reasoning disabled. The composer's effort control opens a four-stop slider: Fast (reasoning off), Low, High and Maximum. Advanced exposes an explicit reasoning switch and the supported effort levels. The selected mode and effort stay fixed throughout the current task and are saved separately for each account, workspace and storage mode. Managed and user-supplied provider efforts are stored separately; previous provider preferences never silently enable Filey AI reasoning.

The managed request carries a strict `reasoning_enabled` boolean. The backend maps false or missing to `thinking.type = disabled` and omits positive reasoning effort, which could otherwise re-enable thinking. Enabled tool runs retain exact provider reasoning within that run. Prior visible assistant replies become labeled quoted context when starting a reasoning-enabled run; Filey does not fabricate reasoning for old chat history. Wallet reservation, usage verification, completion recovery, tool data checks and approvals remain in force.

Routine clear requests use the required lookup and action directly. For an invoice based on the last invoice, the assistant retrieves the matching record, reuses confirmed details in a new draft with a new document number, and verifies the saved result. It does not mark the invoice sent or paid unless requested.

Invoice create/revise tools now honor validated invoice dates, due dates, notes, payment terms, document discount, VAT (including explicit zero) and rounding. Unknown top-level instructions are rejected instead of silently discarded. Copies receive fresh line IDs, and results include the saved document ID. Omitted revision fields retain their current values; explicit empty optional wording/due dates clear them. Overdue reports exclude unsent and cancelled drafts. Receipt totals group by currency instead of adding unrelated face values. Receipt/cheque preflight rejects invalid calendar dates and unsupported cash amounts before writes.

Cloud expense saves require a valid positive record ID from the database receipt. Missing or malformed receipts produce an uncertainty message instead of success. The agent returns the saved expense ID for confirmed saves and marks errors unsafe to retry; it does not replay an unconfirmed expense write.

Account/workspace transitions invalidate a pending agent run and tool approval even if the user returns to the original scope before it finishes. Dispatch, multi-step data reads and pre-side-effect checks capture the monotonic cache identity as well as the scope. Regressions reproduce the stale approval and outbound-send failures using mocked data and transports; returning to the same organization cannot revive a prior approval.

Healthy cloud completion polling checks after 500 ms, 1 second, 1.5 seconds, then every 3 seconds. Transport failures and missing-receipt recovery keep the slower 3-second delay. Five immediately ready rounds incur 2.5 seconds of polling in the timer regression instead of 15 seconds. This is a controlled timing test, not a measured provider response-time promise. Account scoping, single dispatch, active wait budget, background pause and the shared server read limit remain enforced.

Deploy the reviewed `ai-credits` handler and shared dependencies first, then the matching web build. No database migration, price change, credit grant, provider credential change or desktop updater release is required. Provider inference and tool calls still take time; this removes forced reasoning, not all request latency.

Validation covers quick chat/tool turns without reasoning, slider and Advanced interactions, mode/effort pinning across tool rounds, continuing an existing chat after switching modes, preference isolation, recovery, unchanged user-supplied providers, invoice instructions/totals, mixed currencies, stale approval rejection, and frontend/backend type and build checks. No customer records, paid model requests or outbound messages are used for verification.
