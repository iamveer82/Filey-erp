## Confirmed repairs

- Cloud header/line replacement, financial posting and reversal, stock movement, generated sales order, customer advance allocation and private receipt now commit or roll back together. Purchase receiving/payment/removal, order reservation changes, advance deposit changes, journal maintenance and manual stock adjustments use operation-specific RPCs. Ordinary RLS and module checks still apply through a narrowly owned nonlogin/nonbypass dispatcher role.
- Internal mutation/coordination helpers now grant EXECUTE only to the trusted workflow executor. Authenticated, anonymous and service-role clients cannot call posting, ledger, stock, payment, advance or reversal helpers directly to bypass the outer atomic/receipt contract. Pure calculators, bounded permission-scoped boolean gates and authenticated dispatchers remain available. Actual database tests deny direct post/entry/old advance helper calls and verify the normal dispatcher still works.
- Device workflows stage the business effect and receipt in one local transaction. A private CAS-backed request registry preserves the reviewed request and exchange rate after an uncertain acknowledgement. Independent active equal actions keep different request IDs; a foreign live/crashed lease cannot create a new implicit retry identity. Recovery after lease expiration reuses the original ID. Scope is captured before asynchronous registry work and checked immediately before dispatch and after response.
- Payments have immutable payment IDs on their financial bundles. Cash uses payment-date exchange rates, control accounts use saved document rates, and the difference posts to FX. Deletion reverses the complete bundle and the account balances. Paid-state calculation includes advance credit; unposting/changing settlement currency is rejected while payments remain.
- Invoice line totals follow the shared cent-allocation/tax/manual/formula/discount/round-off calculator. Server receipt validation rejects missing, wrong or mismatched parent/payment identifiers; definitive SQL errors clear the pending action while ambiguous transport outcomes retain it.
- A real baseline proved two staff users could consume 120 of a read-only shared 100 advance deposit because each could miss the other's private allocation. New credit spending uses the original invoice author's editable pool, including when an admin acts on that invoice. Admin cross-author funding is refused. Existing verifiable unchanged allocations survive note edits; cancellation releases them. Ambiguous older allocations with a different author from their parent require reconciliation. Actual credit use/release and deposit changes honor the existing people-module gate; freeform zero-credit invoice-only drafts remain supported.
- A separate legacy regression showed a matching invoice/allocation author could still hide borrowing from another author: the original depositor could spend 80 again and leave the party pool at -40. Before new spending or a deposit reduction, the privileged server guard checks every author's net pool for a negative balance. The local guard does the same over current-workspace imported rows. New spending/replacement and unsafe deposit reduction are refused; unchanged invoice allocations keep their IDs on note edits, deposit note edits remain possible, and safely attributable release/cancellation permits reconciliation and restores the original author's usable positive pool. The baseline is executed only in a rolled-back synthetic database transaction with this one new guard removed.
- New cloud child, payment, generated order, stock and financial effects retain their source author. Generated accounts also belong to that author. An original author can save after an admin edit, remove an admin-entered payment and reverse the invoice/purchase order without leaving hidden effects. A boolean privileged preflight rejects incompatible historical modern-ID or legacy-reference effects, foreign/null organization children and ambiguous historical duplicate document references.
- Another actual database regression proved a null/absent invoice type silently skipped stock reversal because SQL NOT(IN(...)) became NULL. The predicate now treats a missing type as a normal invoice; the admin-edit/cancellation test deliberately omits that field.
- Receipts preserve their prior moving-average unit cost. A later external movement requires reconciliation before reversal. A separate baseline proved an old admin-owned later movement could be hidden from the receipt author's RLS and evade this guard. The final permission-scoped boolean check inspects that complete history, exposes no journal values, and rejects the reversal atomically.
- Ledger repair only removes identical source legs with an actual invoice/PO/advance/payment identifier and matching creator. Payment-source legs additionally require the immutable payment ID. Equal manual entries, ref-only history and two equal legacy payments on the same invoice remain untouched. Account opening balances survive reversal; active/source-linked account changes are protected.
- Explicitly foreign organization or other-author advance rows do not enter local pools. A same-org other-author allocation tag is refused before any mutation; other-org tags remain untouched. Imported other-author funds cannot inflate the current author preview or make an already spent own deposit appear deletable. Untagged legacy rows remain in the selected account partition. Unsupported offline mutations of another author's imported business records fail with cloud-mode guidance instead of creating mismatched effects for later upload. This is a deliberate local support boundary, not a claim of offline cloud-admin authority.
- API-generated new document numbers use the root agent's scoped allocator; recurring generation now delegates to its transactional schedule helper and uses the same UTC calendar as the server. Allocation may reserve a number before a later business rejection; such gaps are intentional, and identifiers are not reused.
