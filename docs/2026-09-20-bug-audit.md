# Frontend and backend bug fixes — September 20, 2026

Deployment update: the team and atomic rate-limit migrations are applied and all
seven required edge entrypoints are deployed. See the
[live cloud audit](2026-09-20-cloud-sync-audit.md) for versions and schema checks.

## Fixes

- Module navigation now refreshes after membership, module-setting and reconnect notifications. Permission changes no longer wait for a window-focus event. Database policies remain the authority.
- Billing return handling preserves the HashRouter Settings route. A checkout return URL no longer claims payment succeeded; the screen waits for the verified subscription state. Opening the billing portal on desktop releases the busy state, and payment actions cannot overlap.
- Date-only document values render as calendar dates in every timezone, while timestamps still represent their original instant.
- Purchase includes the first calendar day of the current month regardless of timezone. Its category count includes all categories; only the visual breakdown is limited to six.
- Edge rate limits reserve attempts atomically before provider calls. Concurrent requests cannot all pass the old read-then-write counter, and database errors fail closed. Public checkout addresses work without being cast to account UUIDs. WhatsApp bridge calls and failed provider attempts now consume the configured budget. The email sender uses the same atomic counter.

3. Redeploy `dodo`, `stripe` (if still deployed), `agent-jobs`, `run-tool`, `channel-webhook` and `send-email`, preserving each function's existing authentication configuration and secrets. These functions now require `filey_take_rate_limit`; deploying them before the migration will refuse requests.
4. Deploy the frontend after the backend prerequisites are present.

Budgets count **attempts**, including failed or uncertain provider calls and retries. Windows start at the first reservation and reset after the configured duration, rather than at midnight. Successful-send audit records remain separate. Identities are hashed; app clients cannot read or mutate the counter. One row is retained per identity/action; inactive-counter retention can be handled during database maintenance if traffic warrants it.
